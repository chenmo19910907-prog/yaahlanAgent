# 测试用例自动生成器 (Test Case Generator)

这个技能可以自动从钉钉产品需求文档生成完整的测试用例文档，支持多种文档格式（Excel表格、普通文档），并严格遵循预定义的测试用例设计规则。

## 何时使用

- 需要从钉钉文档生成测试用例时
- 产品需求文档更新，需要同步更新测试用例时
- 需要标准化测试用例输出格式时
- 大量测试用例需要批量生成时

## 适用场景

- **产品需求评审**：基于PRD文档快速生成测试用例框架
- **迭代开发**：新功能上线前自动生成回归测试用例
- **质量保障**：确保测试用例覆盖率和标准化
- **文档同步**：需求变更时自动更新相关测试文档

## 执行流程

### 0. 【强制前置】先读知识库 ⚠️

**生成任何模块的测试用例前，必须先完成知识库对齐，禁止仅凭 PRD 片段盲写用例。**

按以下顺序依次查找并读取，找到即读，不得跳过：

1. **`documents/` 根目录**：根据需求模块名查找同名或近义 `.md`（如 `贵族.md`、`消息.md`、`财富魅力等级.md` 等），完整阅读。
2. **`testcase-kb/` 补充知识库**：按 `rules/version_testcase_generation_rules.md` §1.2 索引表查找本模块对应文件，作为补充知识来源，与 `documents/` 交叉对照。
3. **动态域另查 `documents/moments/`**：功能涉及动态（列表/详情/发布/视频/热度/标签等）时，按 `rules/version_testcase_generation_rules.md` §1.3 索引选取对应 `*.md` 读取。
4. **公会域另查 `documents/Agency/`**：功能涉及公会/公会长时，查找 `documents/Agency/` 下对应文件读取。
5. **若所有路径均不存在**：在输出中明确标注「未找到知识库对照，建议补充模块文档」，再基于 PRD 生成。

> 详细查找规则与索引表见：`rules/version_testcase_generation_rules.md` 第 1 节。

## 生成规则说明

### 用例结构规范
每个生成的测试用例都包含以下标准字段：

```markdown
| 编号 | 子功能模块 | 测试步骤 | 预期结果 | 优先级 | 预估时间 |
|------|-----------|---------|---------|-------|----------|
| AUTH_LOGIN_001 | 登录验证 | 1. 步骤1<br>2. 步骤2 | 预期结果描述 | P0 | 3分钟 |
```

### 优先级标准
- **P0**：核心功能，影响系统正常使用
- **P1**：重要功能，用户常用功能
- **P2**：一般功能，辅助功能
- **P3**：边缘功能，低频使用

### 覆盖范围
- **功能覆盖**：≥95% 的业务功能点
- **流程覆盖**：正常流程 + 异常流程 + 边界条件
- **数据覆盖**：有效数据 + 无效数据 + 边界值
- **平台覆盖**：多设备 + 多系统 + 多网络环境

### 榜单用例（Yaahlan / 活动页榜单）
当用户要生成 **榜单** 相关测试用例，或需求/对话中明确涉及 **活动榜单** 等场景时，**必须先阅读** 仓库内 `templates/yaahlan榜单.md`（及通用参考 `templates/榜单.md` 的列结构：编号、子功能模块、测试步骤、预期结果）：
- 按 **B 列「子功能模块/功能模块」** 维度归类，与现表中的模块划分（如「榜单值统计逻辑」「全服用户送礼/收礼榜」「弹窗热区交互」「榜单奖励」等）对齐。
- 输出用例的 **步骤、预期、颗粒度** 与 `yaahlan榜单.md` 中已梳理用例保持同一风格，再按当前 PRD 增量补全或调整。

## 错误处理

### 常见错误及解决方案

| 错误类型 | 错误信息 | 解决方案 |
|---------|---------|---------|
| 文档访问失败 | "无法访问钉钉文档" | 检查URL有效性，确认权限设置 |
| 解析失败 | "文档格式不支持" | 确认文档为支持的格式（Excel/普通文档） |
| 规则文件缺失 | "找不到设计规则文件" | 确认规则文件路径和文件名正确 |
| 输出权限不足 | "无法写入输出目录" | 检查目录权限，确认写权限 |

### 降级处理
- **文档无法访问**：提示用户手动提供文档内容
- **解析失败**：提供基础模板让用户手动完善
- **规则缺失**：使用内置默认规则生成

## 实践经验与规范（来自真实用例沉淀）

### 输出格式规范

实际使用的是 **3列格式**（无编号）：

| 功能模块 | 测试步骤 | 预期结果 |
|----------|----------|----------|

- **功能模块** ⚠️ 高频错误，严格执行：
  - 只写模块名，**严禁**在模块名后追加任何子场景说明，无论用「-」「·」「—」还是其他符号
  - ✅ `【背景降级】`、`【历史记录弹窗】`、`【游戏客服转单】`
  - ❌ `【背景降级·正在使用时】`、`【历史记录弹窗-强弹】`、`【游戏客服转单-VIP不足】`
  - 不同场景（如 VIP 足/不足、浏览完/未浏览完）的区分应写进**测试步骤**，绝不出现在模块名里
- **连续同模块用例** ⚠️ 高频错误，严格执行：
  - 同一模块名连续多行时，**第二行起功能模块列必须留空**，绝不重复填写
  - ✅ 第1行写 `【转单入口与菜单】`，第2~5行该列为空
  - ❌ 第1~5行都写 `【转单入口与菜单】`
- **预期结果**：一条用例有多个预期时，拆成多行，测试步骤列留空，每行一个预期

### 需求来源为对话而非文档时的处理规范

当需求通过多轮对话逐步建立，没有完整文档可对照时：

1. **生成前做一次结构化确认**：把理解到的核心规则、边界条件、待定项列出来，让用户确认后再生成，避免方向性错误
2. **待定项显式保留**：需求中明确说「待定」的逻辑，不要猜测，直接在预期结果写「以产品最终结论为准，确认后更新」
3. **不要自行补充复杂派单/路由逻辑**：涉及多角色、多入口、多状态的逻辑（如 VIP 管理客服派单），若没有逐条确认，极易写出与需求不符的用例，需主动询问

### 用例覆盖方法

**矩阵式覆盖**：对于「状态 × 行为」的场景，用枚举矩阵拆分，而非合并成一条：

```
状态维度：7日内 / 第8日（TTL已过）
行为维度：直连入口 / 其他入口
角色维度：用户端 / 建联客服 / 非建联客服
```

每个组合单独一条用例，预期结果逐行列出。

**边界值必须显式覆盖**：
- 临界点本身（恰好 = 门槛值）单独一条
- 临界点上方（> 门槛值）一条
- 临界点下方（< 门槛值，如 -0.01）一条

**字段级校验**：列表页的表头字段、详情弹窗字段，需要单独列条目逐项验证，而非合并描述

**基础流程不要省略**：「点击返回按钮」「重置后状态」等基础操作验证，看似显而易见但执行时需要对应 case

**动态效果类需求必查极速模式与设备档位**：凡需求中涉及新增「动态」效果（动态背景、动态头像、动态头像框、动态表情、GIF 等），必须补充以下用例：

- **极速模式**：
  - 开启极速模式后，动态效果降级为静态资源展示
  - 关闭极速模式后，动态效果恢复正常

- **设备档位**（低端/中端/高端设备各一条）：
  - 低端设备 → 动态效果展示为静态图
  - 中端设备 → 动态效果展示为静态图
  - 高端设备 → 动态效果正常播放

### 本地文件管理规范

- 用例统一存放在 `temporary_testcase/` 目录，文件名与需求名一致
- 本地 Markdown 是写入钉钉 Excel 的唯一数据源，以 Excel 最终版本为准时需同步更新本地文件
- 写入 Excel 前确认用户没有手动改动 Excel，若有需提前告知否则会被覆盖

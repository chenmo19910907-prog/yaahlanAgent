# PRD Review — 产品文档理解与审查

## 需求理解入口与索引

生成测试用例前必须先对需求文档（PRD、产品说明、钉钉文档等）进行**结构化理解**，再结合项目规则与用例生成 Skills 生成用例。理解需求时须参考下文「审查流程」与「审查维度」，不得盲生成。

## 定位

审查并理解产品文档是否**把需求讲清楚了**，便于后续**基于需求生成测试用例**。只关注「产品想要什么」（功能目标、用户场景、业务规则、边界与异常），不关注技术实现。生成用例前须先按本 Skill 理解需求并输出摘要，再结合项目规则与用例生成 Skills；流程与知识库见 **.cursor/skills/qa-testcase-agent-system/testcase_agent_system_prompt.md**。

## 审查流程

### Step 1: 判断功能类型

```
├── 房间内玩法（游戏、宝箱、PK、连麦等）
├── 活动/运营（限时活动、榜单、任务、节日活动等）
├── 支付/经济（充值、送礼、提现、商城等）
├── 用户功能（个人页、设置、社交关系、IM 等）
└── 后台/运营工具
```

功能类型决定侧重审查哪些维度，并影响测试用例的覆盖重点（如支付类必覆盖扣款、余额不足、分成）。

### Step 2: 按维度逐项审查

见下文「审查维度」。理解需求时按维度从 PRD 中提炼：核心场景、入口、规则、边界、异常，并记录缺失或模糊项，便于生成用例时补全或标注「待产品确认」。

### Step 3: 输出理解摘要或审查报告

- **用于生成用例时**：输出结构化摘要（功能类型、核心场景、业务规则、边界与异常、多角色差异、待确认点），供用例生成规则与 Skills 使用。
- **用于评审 PRD 时**：可按底部「输出模板」输出审查报告。

## 审查维度

### 1. 功能目标

| 检查项 | 要点 |
|--------|------|
| 背景与动机 | 为什么要做这个功能？解决什么问题？ |
| 目标用户 | 面向哪些用户群体（主播/观众/新用户/付费用户等） |
| 成功指标 | 用什么数据衡量功能是否成功（DAU、留存、付费率等） |
| 优先级 | 哪些是 MVP 必须的，哪些是后续迭代的 |

### 2. 用户场景

| 检查项 | 要点 |
|--------|------|
| 核心场景 | 主流程的用户故事是否完整（谁在什么场景下做什么，期望什么结果） |
| 入口与触达 | 用户从哪里进入这个功能（Banner/弹窗/红点/Tab/推送等） |
| 完整路径 | 从入口到完成目标的每一步交互是否都有描述 |
| 多角色视角 | 不同身份的用户看到的是否一样（如房主 vs 普通观众 vs 管理员） |
| 首次 vs 回访 | 首次使用和再次使用的体验是否有区别 |

### 3. 交互与文案

| 检查项 | 要点 |
|--------|------|
| 页面/弹窗 | 每个页面/弹窗的内容、布局和交互是否有说明或原型图 |
| 按钮行为 | 每个可操作元素点击后的行为是否明确 |
| 加载状态 | 页面加载中、加载失败、无数据时分别展示什么 |
| 文案完整性 | 所有面向用户的文案是否都已提供（标题、提示、错误提示、按钮文字等） |
| 多语言 | 是否提供了所有语种的文案，或至少提供了翻译需求 |
| 动效/动画 | 是否有需要特别说明的动效（如抽奖转盘、礼物特效） |

### 4. 业务规则

| 检查项 | 要点 |
|--------|------|
| 资格条件 | 谁能参与、谁不能参与，判断条件是否明确 |
| 数量/次数限制 | 每人每天/每次的限制，是否有上限 |
| 排序/排名规则 | 列表怎么排序，排名怎么算，并列怎么处理 |
| 奖励/惩罚 | 奖励内容、数量、发放条件、领取方式是否明确 |
| 收费/扣款 | 花多少钱、用什么币种、价格是否需要分区域/平台 |
| 关联功能 | 与现有功能的交互关系（如送礼是否影响亲密度/等级） |

### 5. 边界与异常场景

| 检查项 | 要点 |
|--------|------|
| 网络异常 | 操作过程中断网了，用户看到什么，恢复后什么状态 |
| 退出场景 | 用户中途退出（退房间/杀 App/切后台），进行中的操作怎么处理 |
| 重复操作 | 用户快速连续点击同一按钮，预期行为是什么 |
| 并发冲突 | 多人同时操作同一资源时用户看到什么（如抢同一个麦位/宝箱） |
| 时间边界 | 踩着活动开始/结束的时间点操作，用户体验是什么 |
| 版本兼容 | 老版本客户端遇到新功能时展示什么（降级/提示升级/忽略） |
| 封禁用户 | 被封禁的用户能否看到/参与此功能 |

### 6. 活动运营专项（限时活动必审）

| 检查项 | 要点 |
|--------|------|
| 时间安排 | 活动的完整时间线：预热、开始、结束、奖励发放、展示下线 |
| 时区处理 | 时间是 UTC 还是用户本地时间，跨时区用户看到什么 |
| 地区差异 | 不同国家/地区的规则、奖励、文案是否有差异 |
| 可配置项 | 哪些参数需要运营可调（时间、奖励数量、门槛等），调整是否需要发版 |
| 紧急下线 | 活动出问题时如何紧急关闭，关闭后用户看到什么 |

### 7. 支付经济专项（涉及资金必审）

| 检查项 | 要点 |
|--------|------|
| 币种与价格 | 使用钻石/水晶/现金，价格表是否完整 |
| 付费确认 | 扣款前是否需要二次确认弹窗 |
| 余额不足 | 余额不足时的引导流程（跳转充值？提示文案？） |
| 退款规则 | 什么情况可以退款，退款流程描述 |
| 收益分配 | 涉及分成的场景（主播/公会），分成比例和结算规则 |

### 8. 通知与触达

| 检查项 | 要点 |
|--------|------|
| 推送/通知 | 什么事件需要推送通知，推送文案和跳转目标 |
| 房间内广播 | 什么事件需要在房间内展示消息（公屏/弹幕/特效） |
| 红点/角标 | 哪些入口需要展示红点，红点消除条件 |

## 注意事项

- **只审查产品层面**：不评价技术实现方案。
- **不要编造需求**：基于 PRD 内容审查与理解，不臆测产品意图。
- **生成用例前必用**：理解需求须完成本文件上文「需求理解入口」与「审查流程」，再调用用例生成规则与 Skills；流程与知识库见 **.cursor/skills/qa-testcase-agent-system/testcase_agent_system_prompt.md**。

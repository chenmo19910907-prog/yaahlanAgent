# 版本 Case 生成规则

本文档定义 **发版 / 版本迭代 / 回归** 场景下自动生成测试用例时的规则。与 `testcase_generation_rules.md`（活动与通用业务规则）配合使用：通用数值、榜单、礼包等仍遵循该文件；**版本专项** 以本文档为准。

---

## 1. 强制前置：先读 `documents/` 模块文档

生成 **任意模块** 的版本 case 前，必须先完成 **业务上下文对齐**，禁止仅凭 PRD 片段盲写用例。

### 1.1 查找步骤（Agent 必须执行）

1. 根据用户给出的 **需求模块名 / 功能域**（如：礼物、房间、登录、支付、**动态 / Moment**），在仓库 **`documents/`** 目录下查找同名或近义 Markdown 文件（如 `gift.md`、`room.md`）。**若功能域为动态（列表、详情、发布、视频、热度、标签等）**，须同时在 **`documents/moments/`** 子目录下按 §1.2 索引选取对应 `*.md`，不得只扫 `documents/` 根目录而遗漏子目录。  
2. **若存在**：完整阅读该文档中的 **模块范围、主链路、必查场景、异常与边界说明**，再结合 **本次版本 PRD / 变更点** 生成用例。动态相关时建议 **交叉阅读**：例如改视频链路时同时对照 `documents/moments/video.md` 与 `documents/moments/basic module.md` 中发布/列表/详情章节。  
3. **若不存在**：  
   - 在输出或备注中明确列出 **缺失的 `documents/xxx.md` 或 `documents/moments/xxx.md`**；  
   - 仅基于 PRD 生成时须在每条相关用例或章节头标注 **「未找到 documents 对照，建议补充模块文档」**；  
   - 优先建议产品/测试补充 `documents/`（及动态域时 `documents/moments/`）后再扩写深度用例。

### 1.2 文档与模块映射（维护约定）

| 做法 | 说明 |
|------|------|
| 新增业务域 | 同步在 `documents/` 增加 `模块名.md`，按「功能模块 + 主链路 + 必查场景」结构维护，便于版本回归引用。**动态（Moment）类** 建议统一落在 **`documents/moments/`**，与根目录其他业务文档区分。 |
| 命名 | 根目录优先使用小写、与产品常用叫法一致的文件名，如 `gift.md`、`live_room.md`。`moments/` 下现有文件含 **`basic module.md`**（文件名中带空格）等，Agent 查找时需 **按实际路径拼写**，避免漏读。 |
| 当前索引（示例） | `gift.md` — 礼物面板、送礼场景、礼物类型与展馆等（随仓库更新，生成前以实际目录为准）。 |
| **动态 / Moment（`documents/moments/`）** | 见下表；与 `basic module.md` 文内说明一致：**视频**能力以 `documents/moments/video.md` 为准，**基础列表/详情/发布/审核** 以 `documents/moments/basic module.md` 为准。 |

**`documents/moments/` 文档与版本回归映射（维护约定）**

| 文件路径 | 覆盖能力摘要（版本 case 生成前对齐） |
|----------|--------------------------------------|
| `documents/moments/basic module.md` | 动态 **基础能力**：列表页、详情页、**动态发布**、Profile 入口、互动通知、站内巡查、**超管动态审核（审核 tab）**、帧红点等；一级/二级/预期口径，**发版回归主文档**。 |
| `documents/moments/video.md` | **视频动态**：相册选片与权限、预览与选中、编辑页回填、列表/详情全屏播放、与语音房/1v1 冲突、互动通知缩略图、外显入口、异常与敏感视频等；与 `basic module.md` 第 1、2、5 节联合回归。 |
| `documents/moments/hot.md` | **热度与 Sheet2 同表能力**：热度排序/计算/衰减、hot 标签、发现列表规则、**帖子皮肤**、**可见权限**、**@ 好友** 等；热度/排序改版时 **必读**。 |
| `documents/moments/label.md` | **Topic/标签**：后台创建与管理、App 编辑页 Topic、带标签动态、标签分区与发现页、超管移除、开关与 **上下线** 联动等；标签需求迭代时 **必读**。 |

**触发示例（默认先读 documents）**

- 用户指定「**礼物**版本回归」→ **必须先读** `documents/gift.md`，再叠加版本 PRD。  
- 用户指定「**动态 / Moment** 版本回归」「发版回归动态帧」「动态视频改版」「热度/hot 改版」「Topic 标签改版」→ **必须先读** 上表中与变更点匹配的 `documents/moments/*.md`（常组合阅读 2 个及以上）；再叠加版本 PRD。  
- `basic module.md` 总结中强调 **动态视频** 见 `video.md`；生成 **图文 + 视频** 或 **纯视频** 发版用例时，**不得**只读 `documents/moments/basic module.md` 而跳过 `documents/moments/video.md`。
- 从 PRD 生成动态用例的 **流程步骤、动态专属模块提取/层级拆解/相似模块对齐与自检清单** 见仓库根目录 `moments/moments_testcase_generation.md`（与根目录 `SKILL.md` 同构）。

## 1.5 用例结构原则：模块内聚

> 本节与 `testcase_generation_rules.md` 中「用例结构原则：模块内聚」保持一致，在版本 case 生成中**强制执行**。

### 适用范围

**凡功能有清晰步骤或流程的需求均适用**，包括但不限于：处罚/审核操作、表单提交、支付/充值、设置/配置变更、权限申请、内容发布、活动参与等。

> 判断标准：若该功能可以被描述为「做了 A → 触发了 B → 各端展示/记录 C」，则属于有流程的功能，必须按本原则组织用例。

### 核心原则

**以「业务操作对象」为单位内聚，而非按技术层级（客户端/中台/用户侧/服务端）横向拆分。**

同一操作对象在各端产生的全部影响（页面展示、数据联动、消息通知、日志记录），都写在同一模块内；写完一个对象的所有用例后，再开始下一个对象。

### 每个业务模块内的推荐用例顺序

1. **页面展示**：进入该操作页面后 UI 元素是否正确渲染（布局、文案、图标、初始状态、前置数据回填）
2. **核心操作流程**：正向执行路径（触发操作 → 确认/提交 → 操作成功）
3. **边界值 & 反向用例**：必填项为空、字数/数量上限、频控、幂等、并发等
4. **数据联动 & 记录验证**：操作完成后各端数据是否同步（中台日志、统计数据、状态更新等）
5. **消息通知**：操作触发的 IM 消息、系统通知、站内信是否正确下发给相关用户
6. **多语言 & 适配**：当前模块的多语言文案和屏幕适配（如适用）

### 禁止的组织方式

❌ **不要先把所有模块同一技术层的验证写完，再写下一技术层**

```
# 错误示例（按技术层级拆分，操作与后果割裂）
【超管侧】警告-原因选择
【超管侧】禁言-原因选择
【中台侧】7天处罚记录      ← 所有操作的中台汇总，与各操作割裂
【用户侧】处罚系统消息     ← 所有操作的用户侧汇总，与各操作割裂
```

✅ **每个操作对象的全链路写完，再写下一个**

```
# 正确示例（按操作对象内聚，全链路在同一模块）
【警告】    页面展示 → 原因选择 → 提交验证 → 中台记录 → 用户系统消息
【禁言】    页面展示 → 原因选择 → 备注校验 → 中台记录 → 用户系统消息
【封禁账号】页面展示 → 原因选择 → 备注校验 → 中台记录 → 用户系统消息
[回归] 主链路
[通用] 多语言、屏幕适配
```

### 不同功能类型的对象划分示例

| 功能类型 | 操作对象划分方式 | 每个对象内聚的内容 |
|----------|-----------------|-------------------|
| 处罚/审核 | 每种处罚类型（警告/禁言/封禁） | 原因选择 → 提交 → 中台记录 → 用户通知 |
| 活动功能 | 每个活动组件（Banner/礼包/抽奖/榜单） | 展示 → 参与 → 奖励 → 记录 |
| 表单/配置 | 每个配置项或操作页面 | 展示 → 填写 → 保存 → 生效验证 |
| 支付/充值 | 每种支付方式或金额档位 | 入口 → 选择 → 确认 → 到账 → 历史记录 |
| 内容发布 | 每种内容类型（图文/视频/语音） | 编辑 → 发布 → 展示 → 互动通知 |
| 权限/设置 | 每个权限项或设置开关 | 开启路径 → 生效验证 → 关闭路径 → 边界 |

## 2. 版本 Case 的覆盖目标

在已读 `documents/` 对应模块的前提下，版本用例需额外体现 **「新旧版本之间」** 与 **「升级后业务不断」** 的验证，包括但不限于：

- **安装与升级路径**：覆盖安装、增量升级、跨版本升级（如 N-1 → N、N-2 → N，以 PRD 为准）。  
- **数据与状态迁移**：本地缓存、登录态、草稿、业务数据（订单、背包、礼物记录等）升级后是否一致、无脏数据。  
- **兼容与降级**：老接口 / 老配置 / 开关关闭时行为；服务端未全量时客户端表现（若适用）。  
- **新功能与旧链路共存**：新入口与旧入口、新规则与历史数据同时存在时的边界。  
- **前端页面新旧版本对比**：凡本版本涉及前端页面变更（新增元素、移除元素、顺序调整、文案更新等），必须同时覆盖以下两条路径：  
  - **新版本（当前发版）**：变更后的页面内容、布局、入口、文案均按 PRD 要求正确呈现。  
  - **旧版本 / 升级前后对比**：从旧版升级到新版后，受影响页面的旧内容已被替换或移除，不出现新旧混存（如旧入口残留、旧文案未更新）；未涉及变更的页面保持原有表现，不引入回归。  
  > 适用典型场景：协议排序调整、About 页新增/删除入口、注册页新增必填项、弹窗文案替换等所有 UI 层变更。  
- **回滚与紧急策略**：版本回退、热修开关、强制更新提示等（以 PRD 为准）。
- **屏幕适配**：仅涉及**前端页面变更**时，须覆盖大屏与小屏两种设备，展示正常；**纯服务端需求无需覆盖**。
- **多语言**：所有需求（含纯服务端）均须覆盖英语（EN）、阿语（AR）、土语（TR）、俄语（RU）四种语言环境各自展示正常；RTL 镜像仅在有前端页面时额外验证。  
- **语音房需求 — 神秘人逻辑评估**：凡需求涉及语音房（房间内展示、操作、功能入口等），**必须评估是否影响神秘人逻辑**，适用时按下方「§ 神秘人逻辑」专项规则生成对应用例。
- **跨端 / 跨场景回归**：若 `documents/` 中定义 **必查场景**（例如礼物：**房间 + 私聊 + 群聊**），版本 case 须在 **同一模块文档口径** 下至少抽样或全量回归，不得只测单一入口。  
- **动态域**：`documents/moments/basic module.md` 与 `documents/moments/video.md` 中列表、详情、发布、互动通知、多 tab（发现/关注/我的）等 **重叠能力**，版本 case 须在 **同一口径** 下跨 **列表 + 详情 +（如涉及）发布页** 抽样或全量回归；**热度 / 标签** 改动时额外对照 `hot.md`、`label.md`（路径均为 `documents/moments/` 下）。  

通用用例类型仍须包含：

- 正向用例（正常流程）  
- 反向用例（异常流程）  
- 边界用例（边界值、临界状态）  
- 交互用例（关键路径上的用户操作与系统响应）

### 神秘人逻辑（涉及语音房的需求必须评估）

凡需求涉及语音房（房间内展示、房间内操作、房间内功能入口等），**必须评估该需求是否影响神秘人逻辑**，并在适用时补充以下用例维度：

#### 评估要点

| 检查项 | 说明 |
|--------|------|
| 新功能是否展示用户身份信息 | 若新功能会展示用户头像、昵称、ID、等级等，需验证神秘人状态下是否正确隐藏/匿名展示 |
| 新功能是否涉及用户操作记录 | 若功能会记录或广播某用户的行为（如送礼、上麦、投票等），需验证神秘人的行为是否按规则匿名 |
| 新功能入口或列表是否展示房间内用户 | 若功能展示在场用户列表、操作历史等，需验证神秘人的条目展示规则正确 |
| 新功能是否向非本人展示当前用户数据 | 若功能对他人可见，需验证神秘人的数据在他人视角下匿名正确 |

#### 必须覆盖的用例场景（评估后适用时生成）

1. **神秘人作为操作方**：神秘人在房间内执行新功能操作，其身份在他人视角下按神秘人规则展示（头像/昵称匿名或隐藏）。
2. **神秘人作为被展示方**：在新功能涉及的列表/记录/通知中，神秘人的条目展示符合神秘人规则，不暴露真实身份。
3. **非神秘人视角验证**：普通用户在房间内使用新功能，行为和展示不受神秘人逻辑干扰，功能正常。
4. **神秘人状态切换**：用户从非神秘人切换为神秘人（或反向），新功能中已展示的历史数据/记录按对应规则更新或保持。

> 若经评估该需求与神秘人逻辑无关（如纯服务端配置、无用户身份展示的功能），可在用例备注中注明「已评估，与神秘人逻辑无关，无需覆盖」，跳过本节。

### 老版本相关功能回测（每次发版必覆盖）

每次版本迭代，除验证本次变更点外，**必须对本版本改动所影响的周边功能进行回归回测**，防止新代码引入旧功能回归。

#### 回测范围判断原则

| 类型 | 说明 | 示例 |
|------|------|------|
| **直接改动模块** | 本版 PRD 中有明确修改的功能页面或接口 | 礼物面板改版 → 礼物面板所有已有功能 |
| **强关联模块** | 与改动模块共享接口、数据、状态或 UI 组件的功能 | 礼物改版 → 背包、送礼动效、礼物榜单 |
| **入口级联** | 改动了入口位置/路由/跳转，需回测所有受影响的跳转目标 | 钱包入口下移 → 所有跳转至钱包页的路径 |
| **数据流关联** | 改动影响了某个共用数据字段或状态机 | 用户等级计算逻辑改动 → 所有依赖等级显示的模块 |
| **平台兼容** | 仅改了 iOS 但 Android 共用同一接口 / 逻辑 | 须验证 Android 已有行为不受影响，反之亦然 |

#### 必须生成的回测用例类型

1. **核心主链路不断**：本次改动不影响已有功能的最核心使用流程（如充值流程、送礼流程、登录流程）。
2. **关联页面入口正常**：与改动模块有跳转关系的页面，入口点击跳转仍正常，无404/白屏/崩溃。
3. **数据展示一致性**：改动前后历史数据（如订单记录、背包内容、榜单数据）在新版本展示正确，无乱序、重复或丢失。
4. **状态不被重置**：升级新版本后，用户的本地状态（登录态、草稿、开关设置等）不被意外清空或重置。
5. **未改动模块无回归**：同 PRD 中未提及改动的模块，用例需验证其表现与改动前一致，不引入新 bug。

#### 回测用例标注规范

- 在「功能模块」列中注明 `[回归]` 标签，与「新增」用例区分
- 示例：`[回归] 礼物面板 - 送礼主链路`、`[回归] 背包 - 礼物展示`

### 新接口异常场景（涉及新接口时必覆盖）

若本次版本需求涉及**新增接口**，必须额外覆盖以下两类用例：

| 场景 | 用例要求 |
|------|---------|
| **接口返回 data 无数据（空态）** | 接口正常响应但 data 为空（空列表、null、空对象等），客户端展示正确的空态 UI（空白占位图、提示文案等），不出现崩溃、白屏或异常报错 |
| **接口返回服务异常（错误码/超时）** | 接口返回错误码（如 500、业务错误码）或请求超时，客户端展示对应的错误提示或兜底 UI，不出现崩溃；用户可通过重试等操作恢复正常 |

## 3. 与 PRD、活动规则的关系

| 输入 | 用法 |
|------|------|
| `documents/<模块>.md` 及 `documents/moments/<模块>.md` | 模块能力边界、固定必查项、历史口径；动态类以 `moments/` 下分册为准。 |
| 版本需求 / 钉钉 PRD | 本版本 **变更点、新增点、下线点**；用例需显式标出「回归 / 新增 / 兼容」属性（可在用例标题或模块列中体现）。 |
| `testcase_generation_rules.md` | 活动页、榜单、抽奖、兑换、礼包等 **通用片段** 仍按需引用。 |

**优先级**：`documents/` 模块文档与版本 PRD **冲突** 时，以 **当前发版 PRD** 为准，并在用例或备注中说明 **与 documents 差异**，避免静默沿用过期描述。

## 4. 输出格式约定（以 AM 系统用例为标准）

### 4.1 写入钉钉 Excel 的格式（`temporary_testcase/`）

- 输出路径：默认写入 **`temporary_testcase/`**，文件名建议带模块或需求标识，如 `AM系统_测试用例.md`。  
- **表格列（4 列，固定顺序）**：  
  `编号` | `功能模块` | `测试步骤` | `预期结果`  
- **编号**：带模块前缀 + 三位序号，如 `AM_001`、`AM_135`；一个文件内全局递增。
- **功能模块**：只写大模块标题，使用【侧/端】前缀区分视角，层级用短横线 `-` 分隔，最多两级。禁止将多步骤路径塞进模块名。  
  - 正确示例：`【AM侧】公会列表-筛选`、`【萨克侧】操作栏-删除AM`  
  - 错误示例：`【AM侧】公会列表-筛选-目标已完成`（「目标已完成」属于步骤细节，应写入测试步骤列）  
- **测试步骤**：一句话描述可执行操作，不使用编号前缀（与知识库中 `1. 2.` 编号风格区分）；多个动作用逗号连接。  
- **预期结果**：可验证的界面/数据/提示；多条预期用分号 `;` 分隔。

### 4.2 知识库格式（`documents/` 或 `documents/Agency/`）

生成用例写入钉钉 Excel 后，同时按以下格式保存为知识库文档：

- 文件顶部为一级标题：`# {模块名}`（如 `# AM系统`）。
- **按功能模块分节**：每个模块使用 `## 功能模块：{模块名}`。
- 模块内使用 Markdown 表格，**表头固定 3 列**：  
  `功能模块` | `用例步骤描述` | `预期结果`  
  （不含编号列，编号仅用于 Excel 管理）。
- 同一功能模块的用例连续排列，不交叉打乱。
- 参考文件：`documents/Agency/AM系统.md`。
